    Create `scripts/vectorize-logo.mjs`, a Node ES module that regenerates every brand asset from
    `img/logo.png` in one run. A script rather than hand-edited output is the point: the SVG is
    explicitly provisional per D-01, so improving the approximation later must be a re-run, not a
    re-derivation.

    The naive approach fails, and RESEARCH.md `### Pitfall A` explains exactly how: `potrace` is a
    single-channel threshold tracer, so one pass over the full-colour PNG yields a black-and-white
    silhouette that either loses the green garlic bulb entirely or merges it into the lettering
    mask. Use the layered technique instead:

    1. Load `img/logo.png` with `sharp` and extract two independent binary masks — one isolating
       the white lettering, one isolating the lime-green bulb. Treat the black field as background
       in both. Tune the extraction thresholds against the actual pixel values in the file rather
       than guessing; report the thresholds used in the plan SUMMARY so a later improvement pass
       starts from them.
    2. Run `potrace` separately over each mask, passing the mask's real brand hex as the trace
       colour — white for the lettering layer, lime green for the bulb layer. Do not let either
       layer inherit a default black fill.
    3. Compose the two resulting path elements into one SVG root with a single shared `viewBox`
       derived from the source image dimensions, so the layers register correctly on top of each
       other rather than being independently scaled.
    4. Run the composed result through `svgo` to drop editor cruft, collapse redundant nodes, and
       strip any script or event-handler attribute. A generated SVG served from `public/` is a
       document the browser parses; it must carry markup only.

    Derive all six variants from that one composition rather than tracing six times: **principal**
    is the composed colour logo on the dark brand field; **invertido** swaps the field and lettering
    for use on light backgrounds; **mono preto** and **mono branco** flatten every path to a single
    fill; **ícone** crops to the garlic-bulb layer alone with its own tight `viewBox`; and
    **favicon-source** is the icon layer on a square canvas with even padding, which Task 2 uses as
    the raster source. Write them to `public/brand/` under exactly the six filenames listed in this
    plan's `files_modified` — those paths are what `docs/brand-guidelines.md` will document and what
    a professional vector delivery later overwrites.

    Inject an XML comment at the top of every generated SVG stating, in Portuguese, that the file is
    an approximation traced from `img/logo.png`, that `img/logo.png` remains the official source of
    the logo, and that the file is to be replaced when a professional vector is delivered. D-01 and
    D-02 require this marking to travel with the artefact, not only with the brand guide — a file
    copied out of this repository must still say what it is.

    If the traced lettering comes out visibly mangled — broken counters in the rounded letterforms,
    or paths so noisy that `svgo` cannot reduce them — fall back to the alternative CONTEXT.md
    already sanctions: hand-author approximate paths for the lettering while keeping the traced bulb,
    and say so in the SUMMARY. Do not ship a result you would not show the client.

    Do not modify `img/logo.png`. Do not invent a colour that is not among PROJECT.md's seven hex
    values.

    Next.js's file conventions require. The framework's rules are strict and, worse, silent — an
    icon with the wrong extension is ignored with no build error, so the variant simply disappears
    from the document head and nobody notices until a device shows a blank tab.

    The three required outputs, per RESEARCH.md `### Pitfall B`:

    - `src/app/icon.svg` — the general-purpose icon convention, the only one that accepts SVG. Copy
      the squared favicon source here so modern browsers get a scalable mark.
    - `src/app/apple-icon.png` — accepts PNG or JPEG only, never SVG. Rasterise the favicon source
      with `sharp` at 180 by 180 pixels, Apple's convention. Composite it over the charcoal brand
      field rather than leaving transparency, because iOS renders the home-screen icon on an opaque
      tile and a transparent PNG turns black there.
    - `src/app/favicon.ico` — accepts `.ico` only, and only at the top level of `src/app/`, not
      nested. Produce it from the same source at the conventional legacy sizes. If `sharp` cannot
      emit the `.ico` container directly in the installed version, generate the PNG frames with
      `sharp` and assemble the container in the script; do not substitute a renamed PNG, which some
      browsers reject outright.

    the run. A generator that exits 0 having written nothing is the failure mode this whole stage
    exists to prevent.

    Do not hand-write `<link rel="icon">` tags anywhere. The framework generates the correct head
    tags with the right `sizes` and `type` attributes from these filenames, and a hand-written tag
    competes with it.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| `img/logo.png` (client-supplied asset) → generated SVG → served document | A generated SVG is parsed as a document by the browser, so generated markup is executable surface unless it is stripped. |
| agent-authored approximation → perceived brand identity | An approximation published at a canonical path can be mistaken for the client's real logo and propagate into print, social, and third-party use. |
| `public/` directory → browser | Everything under `public/` is served verbatim at a predictable URL with no processing. |
